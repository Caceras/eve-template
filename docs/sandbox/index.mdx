Every eve agent has one sandbox rooted at `/workspace`. The built-in `bash`, `read_file`, and `write_file` tools use it. Without an authored sandbox file, eve selects the best available environment automatically.

## Use the sandbox

Authored tools and callbacks access the live sandbox with `ctx.getSandbox()`:

```ts title="agent/tools/run_analysis.ts"
import { defineTool } from "eve/tools";
import { z } from "zod";

export default defineTool({
  description: "Run a Python script.",
  inputSchema: z.object({ script: z.string() }),
  async execute({ script }, ctx) {
    const sandbox = await ctx.getSandbox();
    await sandbox.writeTextFile({ path: "analysis.py", content: script });
    const result = await sandbox.run({ command: "python analysis.py" });
    if (result.exitCode !== 0) throw new Error(result.stderr);
    return result.stdout;
  },
});
```

Relative paths resolve under `/workspace`. `run()` returns `{ exitCode, stdout, stderr }`; a nonzero exit code does not throw automatically. Use `spawn()` for a long-running process.

## Define an environment

A sandbox module exports an environment and returns a sandbox from `defineSandbox()`:

```ts title="agent/sandbox.ts"
import { DefaultSandbox, defineSandbox } from "eve/sandbox";

export const environment = DefaultSandbox.environment();
export default defineSandbox(() => environment.create());
```

`environment.create()` creates a persistent sandbox owned by the current eve session. Pass options for the live sandbox to `create()`, then configure the returned sandbox before returning it:

```ts
import { defineSandbox } from "eve/sandbox";
import { VercelSandbox } from "eve/sandbox/vercel";

export const environment = VercelSandbox.environment();

export default defineSandbox(async ({ session }) => {
  const sandbox = await environment.create({ networkPolicy: "deny-all" });
  await sandbox.writeTextFile({ path: ".eve/session", content: session.id });
  return sandbox;
});
```

The environment export is required because `eve build` prepares immutable environment inputs before a session exists.

### Prepare a reusable environment

Use the environment's `prepare` option for setup every new sandbox inherits:

```ts
import { defineSandbox } from "eve/sandbox";
import { VercelSandbox } from "eve/sandbox/vercel";

export const environment = VercelSandbox.environment({
  prepare: async (sandbox) => {
    const result = await sandbox.run({
      command: "sudo apt-get update && sudo apt-get install -y jq",
    });
    if (result.exitCode !== 0) throw new Error(result.stderr);
  },
});

export default defineSandbox(() => environment.create());
```

eve runs `prepare` while creating a reusable provider artifact, not once for each live session sandbox. Vercel captures a snapshot; Docker captures an image; microsandbox captures a VM snapshot; and just-bash captures a filesystem template.

At runtime, eve passes the recorded artifact directly to the provider when it creates a live sandbox. Runtime does not rebuild or repair a missing artifact. A missing image, snapshot, or template fails with rebuild or redeploy guidance.

### Share a named sandbox

`getOrCreate()` shares one provider-owned persistent sandbox across eve sessions that use the same name:

```ts
export default defineSandbox(({ session }) =>
  environment.getOrCreate({ name: `team-${session.auth.current?.principalId}` }),
);
```

eve namespaces the authored name with the sandbox definition, environment generation, and constructor configuration. Calls that reuse a name must use the same configuration; conflicting calls fail. Named sandboxes have provider-owned lifetime, so an attached eve session cannot delete or stop one.

Do not write per-user credentials into a shared filesystem. A named sandbox also has one network boundary for every attached eve session: use one stable network policy rather than deriving it from the current caller.

### Share a parent sandbox

A declared subagent can use its dispatching parent's sandbox explicitly:

```ts title="agent/subagents/reviewer/sandbox.ts"
import { defineParentSandbox } from "eve/sandbox";

export default defineParentSandbox();
```

An inheriting subagent cannot declare its own managed workspace or skill files.

## Managed workspace and skills

Use the sandbox directory for authored workspace seeds:

```text
agent/sandbox/
  sandbox.ts
  workspace/
    schema.sql
```

Files under `agent/sandbox/workspace/` seed writable `/workspace`. eve copies the seed when it prepares a new environment generation. Existing live sandbox state is not overwritten by later seed changes.

Agent skills are compiled into a separate resource tree and exposed at `$HOME/.agents/skills`. These are stable paths across every built-in provider, so instructions and tools can refer to `/workspace` and `$HOME/.agents/skills`. Do not refer to a concrete home directory or `/eve/resources`, which is provider-internal staging.

Providers receive both trees with explicit metadata:

```ts
interface SandboxProviderResourceTree {
  key: string; // Content-addressed identity.
  files: ResourceFile[];
  path?: string; // Materialized build-time source.
  mountPath: string; // Read-only provider mount under /eve/resources.
  targetPath: string; // /workspace or $HOME/.agents/skills.
}
```

Docker and microsandbox mount the compiled trees read-only under `/eve/resources`, copy workspace seeds into writable `/workspace`, and expose skills read-only where possible. Vercel's snapshot environment writes workspace and skill contents before capturing its snapshot. Custom providers decide whether to upload, mount, or write each tree, but must expose the final target paths before authored preparation runs.

## Custom providers

Define a provider with `defineSandboxProvider()` from `eve/sandbox/provider`. The four generic parameters describe environment options, live sandbox options, persisted handle metadata, and the prepared artifact:

```ts
import { defineSandboxProvider } from "eve/sandbox/provider";

export const AcmeSandbox = defineSandboxProvider<
  { image: string },
  { networkPolicy?: "allow-all" | "deny-all" },
  { remoteId: string },
  { templateId: string }
>({
  name: "acme",
  environment(options) {
    const client = createAcmeClient(options);

    return {
      async prepare(ctx) {
        const temporary = await client.createTemporary({
          mounts: await uploadResources(ctx.resources),
          name: ctx.templateName,
        });
        const sandbox = adaptAcmeSandbox(temporary);
        await hydrateResources(sandbox, ctx.resources);
        await ctx.runPreparation(sandbox);
        const template = await client.saveTemplate(ctx.templateName, temporary);

        return {
          artifact: { templateId: template.id },
          reused: false,
        };
      },

      async getOrCreate(ctx, prepared) {
        const remote = await client.getOrCreate({
          existingId: ctx.existing?.remoteId,
          name: ctx.sandboxName,
          networkPolicy: ctx.options.networkPolicy,
          source:
            prepared === undefined
              ? { image: options.image }
              : { templateId: prepared.artifact.templateId },
        });

        return ctx.handle({
          sandbox: adaptAcmeSandbox(remote),
          metadata: { remoteId: remote.id },
          stop: () => remote.stop(),
          shutdown: () => remote.stop(),
          delete: () => remote.delete(),
        });
      },
    };
  },
});
```

`ctx.runPreparation(sandbox)` invokes the callback authored as `environment({ prepare })`. Call it after provider resources are available in the temporary sandbox and before capturing the provider artifact.

`prepare()` returns a JSON-serializable artifact that eve stores by provider and template generation. At runtime, eve passes `{ templateName, artifact }` as the second `getOrCreate()` argument. It passes `undefined` only when the environment has no preparation callback, workspace seed, skills, Dockerfile, or other prepared input. The fourth generic gives both methods the provider's exact artifact type; the provider must explicitly define its unprepared creation path.

`ctx.options` contains options for the live sandbox. `ctx.existing` contains persisted metadata for reconnecting that sandbox. Keep provider SDK values behind the provider so selectors always receive eve's `RuntimeSandboxSession`.

## Providers

| Provider                                   | Use it for                                                                              |
| ------------------------------------------ | --------------------------------------------------------------------------------------- |
| [Default](/docs/sandbox/default)           | Automatic provider selection with eve's standard behavior.                              |
| [Vercel](/docs/sandbox/vercel)             | Snapshot-backed persistent Vercel Sandboxes, domain network policies, and Drive mounts. |
| [Docker](/docs/sandbox/docker)             | Local containers from the default image, an existing OCI image, or a Dockerfile.        |
| [microsandbox](/docs/sandbox/microsandbox) | Local lightweight VMs from an OCI image or Dockerfile.                                  |
| [just-bash](/docs/sandbox/just-bash)       | A pure-JavaScript shell and virtual filesystem without native process isolation.        |

## Lifecycle

Session-owned sandboxes persist across turns and deployments while their provider state remains available. `sandbox.stop()` stops compute without deleting persisted state. `sandbox.delete()` removes a session-owned sandbox; the next `ctx.getSandbox()` creates a fresh sandbox from the current environment.

Changing sandbox source, preparation code, Dockerfile content, environment options, workspace resources, or skills produces a new environment generation. Existing durable sessions retain their recorded sandbox state; new sessions use the current generation.
