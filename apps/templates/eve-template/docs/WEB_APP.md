# Web app, notifications, tasks, memory, images and voice

The web app is Ægentica's main channel. It installs like a native app (a
Progressive Web App), keeps every conversation on the server, runs scheduled
tasks on its own, notifies the operator's devices when a result is ready, and
lets the operator see and edit what it remembers.

## Install the app

- **Android (Chrome)**: open the site, then **Settings → Notifications → Install**,
  or the browser menu's **Install app**.
- **iPhone and iPad (Safari)**: tap **Share → Add to Home Screen**. Notifications
  on iOS work only from the installed app (iOS 16.4 or later).
- **Desktop (Chrome, Edge)**: the install icon in the address bar, or
  **Settings → Notifications → Install**.

The installed app opens in its own window with shortcuts for **New chat**,
**Tasks**, **Agents** and **Settings** (long-press the icon on Android), each with
the glyph the sidebar uses. The manifest is `app/manifest.ts`; the icons are
generated by `app/icons/[file]/route.tsx`: the Æ monogram, a maskable version
for Android's adaptive shapes, a white silhouette that Android's **Themed
icons** tint to the wallpaper, and the shortcut glyphs. Android refreshes an
installed app's icons on its own schedule (at most daily, while charging on
Wi-Fi), so new icons can take a day or a reinstall to appear.
`public/favicon.ico` (16 to 48 px, rendered from `app/icon.svg`) answers
browsers and link previews that ask for `/favicon.ico` directly.
Branded images in `public/screenshots/` (four phone and one desktop, the real
app framed with a headline on the brand's black canvas) give Android and
desktop Chrome the richer install dialog; `node scripts/install-screenshots.mjs`
regenerates them from a local test server after a visible UI change. Opening the app again reuses its window instead of starting a
second one, and it follows the device's orientation.

Once installed on Android, Ægentica appears in the system **Share** sheet.
Shared text or a link opens a new chat with it already in the message box
(`app/_components/home-chat-page.tsx`); if the app is signed out, the draft
waits until sign-in. Shared photos, PDFs and text files (up to four) arrive as
attachments of that new chat, with the same size and type checks as the
attachment button. The service worker receives the share at `/share`;
`app/share/route.ts` only answers before the worker is running and keeps the
text. Short text travels in the address (`/?title=&text=&url=`); text too long
for an address (which the server would refuse with HTTP 431) goes through the
tab's session storage instead, so a long article or a non-Latin text arrives
whole. The fallback refuses a post from another website (`Sec-Fetch-Site:
cross-site`, 403); the share sheet's own navigation is not cross-site. The
service worker cannot see that header, so while it runs such a post can still
prefill an unsent new-chat draft, which nothing sends without the user.

On the desktop (Chrome or Edge), the installed app appears under **Open with**
for images, PDFs and text files (`file_handlers` in the manifest); opened files
become attachments of a new chat (`lib/pwa/file-launch.ts`), as shares from
Android's share sheet do. Files dragged anywhere onto a chat window attach to
the message. ⌘+Shift+O starts a new chat, ⌘+B shows or hides the sidebar, ⌘+,
opens Settings and Escape stops a streaming reply, next to ⌘+K for search, which
lists them all. That is on a Mac, iPad or iPhone; elsewhere the key is Ctrl, and
the hints show the key of the device. On Apple devices Ctrl keeps its
text-editing meaning (Ctrl+B, Ctrl+K) in the message box. Enter that confirms an
input-method composition (Japanese, Chinese, Korean) never sends the message or
an answer to Ægentica's question. A message longer than 8,000 characters stays
in the box, unchanged, with a notice of the limit and its length.

On Android the page shrinks above the on-screen keyboard
(`interactive-widget=resizes-content`), so the message box stays visible while
typing.

The installed app behaves like a native one: pulling down never reloads the
page, the keyboard only appears when a text field is tapped, menus open on tap,
the navigation drawer follows a swipe from anywhere on the page (and closes with
a swipe or a tap outside it), and the back gesture closes whatever is open (the
drawer, search, the model picker, any dialog or menu) before leaving the page.
A long press on a chat in the sidebar opens its Rename and Delete menu instead
of Chrome's link menu, and in-app links never offer "Open in new tab". Without a
connection the top bar says **Offline**, and the offline page carries on by
itself once the connection (or, during a deploy, the server) returns. The chat list catches up on its own, since
there is no pull-to-refresh: when the app comes back after 15 seconds away,
when the connection returns, and when a task result arrives as a notification,
so chats started, renamed or deleted on another device show up without a
restart. On phones, **Share** under a reply and the share button in a chat's
top bar open the device's share sheet; desktops copy instead. The installed app asks Chrome to keep
its storage, so unsent drafts and attachments survive storage pressure. The
first frame after a reload already shows the home page's composer with the last
model name this device used.

The strip behind Android's gesture bar belongs to Chrome. Chrome 155 makes it
transparent for installed apps but, unless its
`chrome://flags/#web-app-short-edges-cutout-mode` switch is on, does not let the
page draw behind it, so Chrome's black window shows through. With the switch on
(and by default once Chrome ships it), the app draws under the status and
gesture bars like a native app: it already opts in with `viewport-fit=cover`,
the shell starts its content below the status bar
(`env(safe-area-inset-top)`), and the composer and drawer keep clear of the
gesture bar (`env(safe-area-inset-bottom)`).

`public/sw.js` is a deliberately small service worker. It shows notifications,
badges the app icon until the app is opened again, tells an open app window to
refresh its chat list, opens the right chat when a notification is tapped
(it focuses an open app window first, then takes it to the chat; a window it
does not control, such as one after a hard reload, is asked to go there
itself; a notification only ever opens a path of this app, never `//host`
or another site, which the server does not send either), and serves a branded offline page (`public/offline.html`) with its
cached mark when a page cannot load. Navigation preload starts each
page request while the worker boots. It does not cache the app itself, so a
deploy is visible on the next load. It is registered in production
only (`app/_components/pwa-registration.tsx`).

A page load that meets the server restarting during a deploy (the proxy's
bare 502, 503 or 504) gets the same offline page instead: online, it says the
server is not answering, asks again every five seconds while in view and loads
the page by itself once it answers. API answers and the app's own errors pass
through unchanged.

An app left open across a deploy moves to the new version by itself
(`lib/pwa/version-recovery.ts`). Each build carries its release
(`lib/release.ts`); when the app comes back to the foreground after 15 seconds
or more away, it asks `/api/health` for the server's release and reloads once
if a newer one is live: at once when nothing is in progress, otherwise the
next time it goes to the background. It never reloads during a streaming
reply, while a chat is being prepared or while the microphone is on, nor over
text typed in the visible app. A send or reply that reaches the new server
before that (the old page's Server Actions and lazily loaded files are gone
after a deploy) says **Ægentica was updated** instead of a raw error and
reloads once, with the unsent message kept as a draft. Every automatic reload
is remembered for the tab, so a page that still fails afterwards shows its
error with **Reload** instead of reloading in a loop. A page that fails to
render shows the product's error state, inside the chat shell where possible
(`app/(chat)/error.tsx`, `app/error.tsx`, and `app/global-error.tsx` when the
root layout itself fails), never the framework's default.

## Notifications

**Settings → Notifications → Turn on** asks the browser for permission and
registers the device for [Web Push](https://developer.mozilla.org/docs/Web/API/Push_API).
**Send test** delivers a test notification to every registered device. Turn
notifications on separately on each device that should receive them.

- The server generates its VAPID key pair on first use and stores it, with the
  device list (at most 20), AES-256-GCM encrypted in `settings/push.enc`
  (`lib/push-notifications.ts`). No push service account or environment
  variable is needed.
- Devices the push service reports as gone (HTTP 404/410), or refuses because
  they subscribed with a key the server no longer has (HTTP 401/403), are
  removed automatically. Opening Settings re-registers the current device, so a
  lost device list heals itself, and replaces a browser subscription made with
  an older key (the server's key pair was lost or recreated) with one for the
  current key (`lib/pwa/push-subscription.ts`).
- Signing out removes this device's subscription on the server, while the
  session still allows it, and in the browser, so a signed-out device gets no
  more task notifications.
- The notification API (`/api/settings/notifications`) requires the operator
  session and same-origin POSTs, like the other settings APIs.

## Tasks

The **Tasks** page (`/tasks`, in the sidebar) lists every scheduled task with
its schedule, next run and a link to the latest result.

- **Create → Create with Ægentica** opens a new chat to describe the task in
  your own words; **Create → Set up manually** opens a form: a name, what
  Ægentica should do, and when: once, every day, every weekday, every week,
  or a custom cron expression. New tasks start at the next 08:00 in the
  browser's time zone.
- Search and the **All / Active / Paused / Completed** filters narrow the list.
- **Run now** runs a task once within a minute without changing its schedule: a paused task stays paused and a one-time task still runs at its own time.
- Each run is reported as it ended: finished, failed (with the reason in words, such as a provider out of credits) or waiting for your answer, on the Tasks page, in the notification and in Telegram. A check told to report only when something changed stays quiet when nothing did: its chat is saved, but no notification or Telegram message is sent.
- **Edit**, **Pause/Resume** and **Delete** are in the row's menu.

Each run starts a normal agent session as the operator, saves it as a chat
titled after the task (so it appears in the sidebar on every device and can be
continued), sends a notification that opens the chat, and mirrors the answer to
Telegram when linked. The agent can also create and change tasks from chat; you
confirm each new task and each change to what or when a task runs. The
scheduler, limits and retry rules are in
[TELEGRAM_AND_SCHEDULES.md](./TELEGRAM_AND_SCHEDULES.md#scheduled-tasks).

## Images and voice

**Images.** The agent's `generate_image` tool (`agent/tools/generate_image.ts`)
creates pictures with the AI SDK's `generateImage` through the active provider
and its saved key, so no extra account is needed. The default model is
`openai/gpt-image-1-mini`, which both AI Gateway and OpenRouter offer;
`AEGENTICA_IMAGE_MODEL` overrides it. Images are saved on the volume
(`media/` beside `settings/`, `lib/media-store.ts`) and served only to the
signed-in operator from `/api/media/<name>`, so they reappear after a reload
and on other devices. The chat shows them under the tool line
(`components/chat/message.tsx`), and a Telegram chat receives them as photos;
the model only receives a short summary. A tap opens the full-screen viewer
(`components/chat/image-viewer.tsx`) with
pinch-to-zoom, **Save**, and on phones **Share**, which sends the picture
itself through the share sheet; the Images page offers the same.

A reply's own markdown shows pictures only from `/api/media/`, `data:image`
and `blob:` URLs. Any other image (an address a model could have been tricked
into writing, with data in its query string) renders as a link labelled with
its alt text, or "External image", which opens only when tapped
(`lib/markdown-images.ts`, shared by every place that renders model text). The
`img-src` of the Content-Security-Policy holds the same line in the browser.

**Voice.** Dictation uses the device's built-in speech recognition; spoken
replies use an OpenRouter voice when a key is saved, and the device's own
voice otherwise:

- Dictation: the microphone in the message box uses the browser's speech
  recognition (Chrome and Android use Google's recogniser, Safari Apple's).
  Tap to start, tap again or send to stop. Browsers without it hide the button.
- Voice conversation: the talk-and-listen button keeps the screen on while the
  conversation lasts (the Screen Wake Lock API), so the phone does not dim and
  stop listening between turns. The reply is read with the same voice as
  Read aloud, and listening resumes when it finishes.
- Spoken replies: every finished reply has **Copy** and **Read aloud**, which
  skips markdown, links and code but keeps minus signs (-5°C), dates and
  hyphenated words. **Settings → Voice** chooses the voice: this device's
  voices (free), or one of OpenRouter's text-to-speech models and its voices,
  with a preview in the chosen language. The list comes from OpenRouter
  (`GET /api/v1/models?output_modalities=speech`, cached six hours with a
  bundled fallback, `lib/voice/speech-catalog.ts`); the recommended ones
  (Gemini 3.8 Flash TTS, Grok Voice, MAI-Voice-2, Voxtral, MiniMax, Aura-2,
  Kokoro, the free Flux voices) come first with a note and their price. With
  an OpenRouter key and no choice yet, Gemini 3.8 Flash TTS with the Kore
  voice applies. **Speed** and **Read replies aloud** (speak each new reply
  automatically) stay per device.

The OpenRouter voice is an operator setting shared by every device
(`settings/voice.json`, `/api/settings/voice`), because it spends the saved
key; language, speed and Read replies aloud are per device, like a microphone
choice, in the browser's storage (`lib/voice/preferences.ts`). Speech itself
goes through `POST /api/voice/speech` (`lib/voice-speech-handler.ts`): the
signed-in app sends the text in sentence-sized pieces (the first one short, so
speech starts within a second or two), the server calls OpenRouter's
`/audio/speech` with the saved key and streams the MP3 back, and the browser
plays the pieces in a row while fetching the next one
(`lib/voice/openrouter-speech.ts`). The key never reaches the browser, the text
is capped at 4,000 characters per piece, and requests are rate limited. A
voice that cannot start (no credits, offline, a model that is gone) says why
under the reply and the device voice reads it instead. Phones only play audio
a tap started, so the tap that sends a message or starts a conversation
unlocks the player for the reply. `lib/voice/speech.ts` holds `speak()`,
which routes between the two.

## Logos

Model makers, providers, accounts and services show their real logos, in
the app's monochrome style: the model picker and the composer's model
button (by maker), the AI Gateway and OpenRouter cards, Connections, the
GitHub and Telegram panels, Capabilities (including every registry channel
and service with a published logo), and tool calls of connected services in
a chat. The files live in `public/brands/`; `pnpm brands:sync`
(`scripts/sync-brand-icons.mjs`) regenerates them from pinned Simple Icons
and LobeHub Icons releases, with attribution in `NOTICE`.

## Settings

Settings has five sections with a side menu (on phones a snap-scrolling row that stays pinned under the top bar while the page scrolls):
**Models** (providers, keys and the default model), **Voice**, **Notifications**
(install and notifications for this device), **Connections**, and **Security**. Connections lists what Ægentica can use in the shape of a
plugin directory: built-in tools (web search, image creation, files and code,
voice, memory, tasks), accounts (GitHub and Telegram, set up in place) and work
apps through Vercel Connect (Linear, Notion, Sentry). **Browse directory** opens Capabilities → Explore with the official eve registry surface.

## Memory

The **Memory** page (`/memory`, in the sidebar) shows what Ægentica
remembers about the operator across the app, Telegram and scheduled tasks.
Entries can be added, edited and removed, and **Import** takes a pasted list
(one per line, up to 60 at a time; bullets and numbering are stripped), for
example ChatGPT's Settings → Personalization → Manage memories. Afterwards the
page says how many memories were imported and how many lines were skipped as
already saved or repeated; a longer list is refused whole with a message
rather than cut off.

The page edits the same document the agent uses. Memory is eve's built-in
`fileMemory()` provider in the `profile` slot (`agent/memory/profile.ts`),
stored in `profile.sqlite` inside `EVE_MEMORY_DIR` (`agent/lib/durable-memory.ts`).
The agent saves with `profile__save_memory` when asked to remember something
and removes with `profile__remove_memory`. `lib/memory-store.ts` reads and
writes that document in the provider's own versioned format and with its
limits: 8,000 characters of recalled memory, about 2,000 per entry, duplicates
skipped. Each edit bumps the document version, so a concurrent agent save
retries rather than overwriting it.

eve derives each document's storage key from the memory scope and does not
expose it, so the agent records which key belongs to the operator on its first
recall (`memory_owner` table). Until the operator has sent one message, the
page says memory starts with the first message. Memory is off, and the page
says so, when `EVE_MEMORY_DIR` is not set.

## Chat history

In password mode (the self-hosted default) chats are stored in SQLite on the
persistent volume, not in the browser, so the desktop browser and the installed
app on a phone see the same conversations. The file defaults to
`chats.sqlite` next to the memory directory (the parent of `EVE_MEMORY_DIR`, so
`/app/.eve/.workflow-data/chats.sqlite` in the Docker image). `EVE_CHAT_DB_PATH`
overrides it. Both the web process and the eve process (for scheduled tasks)
use it; SQLite's write-ahead log keeps them consistent. The chat list, a
chat's history and the model catalog (`/api/chats`, `/api/chats/<id>`,
`/api/models`) travel as gzipped JSON to browsers that accept it
(`lib/http/json.ts`); Next.js compresses pages but not route handler answers,
and a long chat shrinks about twentyfold.

An open chat follows its conversation as it happens, not only its own
replies: a result that background work reports back (a delegated agent, a
review that "returns to this conversation"), or a turn sent from another tab
or device, appears and is saved as it arrives, including while a question or
approval from that work waits for an answer. Opening a chat, or coming back to
it, first reads everything eve recorded since the chat was last saved and then
keeps reading until the page is left. A message still being sent when the page
closed is sent again only if eve never received it; otherwise its reply
continues where it was. Each event is shown and saved once, whichever reader
(the chat's own, or eve's hook after a send) delivered it
(`app/_components/agent-chat.tsx`, `lib/chat/event-log.ts`).

A long chat stays quick while a reply streams: the saved history is turned
into messages once per save, each arriving event is applied on top of that,
only the message that changed re-renders, and the browser lays out only the
settled messages near the screen (`content-visibility: auto`), so scrolling to
the end and find-in-page still reach every message.

eve ends a conversation's session for good 30 days after it started
(`sessionTimeoutMs` in `agent/agent.ts`), when the session fails, when
**Activity → Reset** retires it, or when a release changes eve's version
(`docs/production-release.md`), and then refuses every message. The chat
notices (from its log, or from eve refusing the message) and sends the message
into a new session instead, with a quiet line in the conversation where it
started over: Ægentica does not remember the messages above it. Reset in
Activity also clears the session from the chat that used it.

While a chat is open, the window, browser history, app switcher and share sheet show its title ("Plan the trip · Ægentica"), and the next page gets its own title back.

Each chat's menu in the sidebar (**⋯**) has **Rename** and **Delete**. A chat
is named after its first message until renamed; renaming keeps its place in the
history, and the new name shows on every device and in Search. A rename or
delete the server refuses (offline, an error) keeps its dialog open and says
so; a refused rename puts the old name back. Deleting a chat removes it from the
history and `chats.sqlite`; eve's workflow data on the volume keeps its
transcript ([production-release](./production-release.md#data-retention-and-disk-use)).

Chats saved in a browser by an older version are imported automatically on the
first visit after the upgrade, oldest first; each local copy is removed only
after the server confirms it. With `DATABASE_URL` set (the Vercel production
mode), chats are stored in Postgres instead.

## Main composer and workspace navigation

The main persisted chat now has the same attachment path as eve's official client: structured AI SDK file content sent through `useEveAgent`, not a separate upload server. Attach or paste PNG/JPEG/WebP/GIF images, PDF or text: at most four files and 6 MB total per turn. Files persist in this device's IndexedDB through draft, provisional chat and canonical chat navigation, then clear after an accepted send. Opening a chat sends its history once, from `/api/chats/:id`; the page itself only checks that the chat exists (a chat with a 2.4 MB photo used to transfer it twice, in the page and again from the API). Sent files show in the message they came with, as on the native page: a picture as a thumbnail that opens the full-screen viewer, any other file as a chip with its name, type and size (`components/chat/message.tsx`). The typed text is kept too, per chat, in this device's storage (`lib/chat/draft-text.ts`), so a half-written message survives Android closing the app in the background or a reload; sending clears it. Unsent files are device-local, not synchronized to other devices. Without site storage (blocked site data, some private windows) text messages still send; attachments and agent or skill choices need it and say so rather than pretending files were sent. Sign-out clears local composer drafts, text and files and reloads the app, so Back cannot show the signed-in pages kept in memory. Image input requires a catalog model marked Vision; changing to an incompatible model yields a recovery error. Model support for documents can still vary by provider.

Type `/` in the message box to pick a skill and `@` to pick a saved agent for the next message (`components/chat/composer-mentions.tsx`): a list opens above the box, filtered by what follows the trigger; arrow keys move, Enter or Tab (or a tap) picks, Escape closes, and the typed trigger is removed. The pick shows as a chip above the box with its own remove button; "Chat" and "Ægentica" are the first entries and put things back. The skill list is read from the runtime (`/eve/v1/info`), so every file in `agent/skills/` appears without app changes; Chat leaves the choice to the agent, which loads skills by their description. The list and Tasks show that description as a short summary for people: its first sentence, without the model-facing "Use when the user asks…" lead-in (`skillSummary` in `lib/skills.ts`). A chosen skill travels in the `x-aegentica-skill` header and becomes a turn instruction to load it; it is not a new runtime or permission. The attach button sits in the box's footer beside the model. Images → Create opens chat with an image request, and the agent picks `make-an-image` itself. Voice retains the device dictation/hands-free loop and the read-aloud path above, not native real-time audio/video.

A new chat begins as one motion: the home page keeps the greeting and the box in the upper part of the page; Send fades the greeting, glides the box to the bottom, settles the message above it with "Thinking…", and only then opens the chat route, whose first frame (and the route's loading state, `app/(chat)/chat/[id]/loading.tsx`) draws the same picture, so nothing flashes or jumps. `prefers-reduced-motion` skips the glide. A reply then arrives at a steady pace, whole words fading in, rather than in the bursts the network delivers (`useStreamingText` in `components/chat/message.tsx`); the model's reasoning shows its newest lines while it thinks and folds to "Thought for 12s" when the answer starts, and a tap on that line opens or closes it (a fold or unfold by hand is kept). "Thinking…" shows only while nothing else on screen is in progress.

While a reply streams, whether this page sent it, resumed it after a reload or Back, or another tab or background work started it, the primary composer remains available for a correction (placeholder "Add a correction…"). Sending that correction uses eve's documented `turnPolicy: "steer"`, so it stays in the same turn. Stop cancels the running turn through eve: eve's hook `cancel()` for a turn this page started, the session's own cancel for any other reply (resumed, corrected, answered or started elsewhere); a stop that fails says so in the error toast while the reply continues. A new chat that cannot be created returns to the home page with the message back in the box and the reason in the error toast. A message the composer cannot send yet (the previous one is still on its way, or the reply cannot take a correction) stays in the box with the reason in the error toast, never silently. Saving a chat goes through server actions that return a code and a readable message instead of throwing (`app/actions/chat.ts`, `lib/chat/errors.ts`), so a failure never reaches the toast as a framework message: without a connection the toast says so and the message stays in the box, and an expired sign-in opens the sign-in dialog with the message kept, in its chat (or on the home page for a new chat) after signing in again. Normal input remains blocked while waiting on authorization/HITL. A connection's sign-in prompt has **Connect** and **Skip**; Skip ends the turn that waits for the sign-in through eve's cancel, so the conversation keeps its session and everything said in it, and the chat takes the next message once eve confirms. Approval and question controls stay disabled while an answer is on its way, so a double tap sends one answer, and a typed answer stays in its field until eve accepts it (eve keeps a refused prompt open). A tool call whose turn ended before it ran (stopped, failed, or an approved call eve did not carry out) reads "Not run", never complete. This matches the capability already exposed by the advanced Live session instead of hiding it there.

`/agents` creates saved profiles and `/images` lists generated images, with authenticated details, prompt/model metadata when present, save and confirmed deletion. Older images without metadata remain readable. The gallery dates every image file (up to 20,000 directory entries) and lists the newest 1,000, 48 at a time; the limit is disclosed. Pages count back from the oldest listed image, so an image made while paging appears at the top on the next refresh instead of repeating an item. Media responses are `private, no-cache` with a strong `ETag` and `Last-Modified`: the device keeps a picture, but asks the server before every use, so it is still refused after sign-out, and an unchanged picture costs a 304 instead of a download. Deleting an image also removes it from chats referencing that file.

The sidebar uses shared navigation metadata. Global Search (Cmd/Ctrl+K) includes pages, actions, settings and up to 100 recent conversations, fetched in one request each time it opens. Its code loads when the browser is idle or on first use (`app/_components/command-menu-launcher.tsx`), not with every page; the shortcut and the Search buttons work from the start. The advanced AI Elements Live session remains searchable without becoming a second primary chat. Mobile navigation uses the existing Radix Dialog for focus management and Escape handling, with an isolated touch-swipe adapter: swipe right anywhere to open (Android reserves the screen edge for Back) and swipe left on the drawer to close; the drawer slides in from the left. It has one internal scroll owner, closes on navigation, and closes when resized to desktop. See [Agents and orchestration](./AGENTS_AND_ORCHESTRATION.md).
